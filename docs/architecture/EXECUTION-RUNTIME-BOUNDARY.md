## 1. Canonical Architecture Statement

> **MCP is the protocol plane. Execution Runtime is the execution plane. Neither owns the other.**

This repository implements the **Node Execution Runtime** — one of two execution runtime classes beneath the MCP Protocol Plane:

```
                    MCP Protocol Plane (Rust — librarian-mcp)
                           │
                           │ ExecutionRequest
                           │ (tool, arguments, authorization_reference)
                           ▼
                 ┌─────────────────────┐
                 │ Execution Runtime   │
                 │ Contract            │
                 └─────────────────────┘
                           │
              ┌────────────┴────────────┐
              │                         │
              ▼                         ▼
   ┌──────────────────┐    ┌──────────────────────┐
   │ Core Execution   │    │ Node Execution        │
   │ Runtime          │    │ Runtime               │
   │ (macOS — Swift)  │    │ (THIS REPOSITORY)      │
   │                  │    │                      │
   │ authoritative    │    │ delegated execution   │
   │ state mutation   │    │ evidence generation   │
   │ governance       │    │ local substrate       │
   │ custody          │    │ result return         │
   └──────────────────┘    └──────────────────────┘
```

### 1.1 Key Invariants

| ID | Invariant |
|----|-----------|
| **ER-I-001** | MCP is the protocol plane. Execution Runtime is the execution plane. Neither implements the other's role. |
| **ER-I-002** | Core and Node are implementations of the same execution contract with different authority scopes. |
| **ER-I-003** | Authorization always precedes execution. The runtime validates authorization exists; it does not grant it. |
| **ER-I-004** | Runtime identity is always recorded in provenance. Every receipt identifies its producing runtime class. |
| **ER-I-005** | A receipt's authority does not depend on which runtime produced it. Evidence authority comes from the chain. |

## 2. What This Repository Is

**Librarian-Node** is a cross-platform **Node Execution Runtime**. It:

- Receives authorized execution requests from the MCP Protocol Plane
- Validates that authorization is present and non-empty
- Executes the requested operation on the local platform (Windows, Linux, or future target)
- Produces execution evidence (logs, output, metrics)
- Returns an `ExecutionResult` with a schema-compatible receipt and provenance envelope

### 2.1 What This Repository Is NOT

| Misconception | Correction |
|---------------|------------|
| "This is the Rust MCP implementation" | ❌ MCP is a separate protocol plane implemented in `librarian-mcp`. This repo consumes MCP-authorized requests; it does not implement MCP. |
| "This replaces the Swift runtime" | ❌ Core (macOS/Swift) and Node (Rust) are complementary. Core owns authoritative state and governance finalization. Node owns delegated execution and evidence. |
| "This is a second protocol authority" | ❌ There is one MCP protocol plane. This repo is an execution runtime beneath that plane. |

## 3. Execution Runtime Contract

Both Core and Node runtimes implement the same execution contract:

### 3.1 ExecutionRequest (input)

| Field | Required | Description |
|-------|----------|-------------|
| `execution_id` | Yes | Unique execution identifier. Generated by MCP protocol plane at authorization time. |
| `tool` | Yes | Tool/capability name. Must be registered in the node's dispatch table. |
| `arguments` | Yes | Tool-specific arguments. Schema defined by tool registration. |
| `capability_id` | Yes | Resolved capability identity from MCP dispatch. |
| `capability_version` | Yes | Version of the resolved capability. |
| `authorization_reference` | Yes | AG-LINK-000 or equivalent authorization decision reference. |
| `runtime_target` | Yes | `core` or `node`. Node must reject requests targeted at Core. |
| `session_context` | Yes | Session, project, and identity context for provenance binding. |

### 3.2 ExecutionResult (output)

| Field | Required | Description |
|-------|----------|-------------|
| `status` | Yes | `success` or `error`. Determines receipt `final_state`. |
| `result` | No | Execution output. Present on success. |
| `error` | No | Error detail. Present on failure. Must include `recoverable` flag. |
| `evidence` | Yes | Evidence references produced by this execution. |
| `receipt` | Yes | Execution receipt conforming to `execution-receipt.schema.json`. |
| `runtime_identity` | Yes | `runtime_class: "node"`, `implementation: "rust-node-runtime"`, `version`. |

### 3.3 Receipt Requirements

Receipts produced by this runtime must conform to `execution-receipt.schema.json`:

```
Schema:   execution-receipt.schema.json
Version:  v1
Required: execution_receipt_id, execution_id, identity_id,
          admission_reference, final_state, lifecycle_history,
          invoked_capabilities, evidence_references,
          integrity_hash, sealed_at
```

**ER-REC-001**: Core and Node receipts are interchangeable for evidence verification. A verifier must not need to know which runtime produced a receipt to validate it.

**ER-REC-002**: `sealed_by` documents the runtime class. Node receipts set `sealed_by` to the Node runtime identity.

### 3.4 Authorization Rules

| Rule | Description |
|------|-------------|
| ER-AUTH-001 | Authorization is established before the runtime receives the request. The runtime validates that authorization exists; it does not grant it. |
| ER-AUTH-002 | Missing or invalid `authorization_reference` must return an error and produce no receipt. Fail-closed. |
| ER-AUTH-003 | No execution path may bypass the authorization check. |

## 4. Core vs Node: Authority Scope

| Operation | Core Runtime | Node Runtime |
|-----------|-------------|--------------|
| Capability identity resolution | ❌ (MCP owns) | ❌ (MCP owns) |
| Authorization (AG-LINK) | ❌ (MCP owns) | ❌ (MCP owns) |
| Tool dispatch routing | ✅ Routes | ✅ Routes |
| State mutation (governance) | ✅ Owns | ❌ |
| State mutation (local) | ✅ | ✅ |
| Receipt production | ✅ | ✅ |
| Evidence authority | ✅ Final | ✅ Provisional |
| Sprint sealing | ✅ Only | ❌ |
| Capability qualification | ✅ Only | ❌ |

### 4.1 Node Prohibitions (from contract)

| Prohibition | Rationale |
|-------------|-----------|
| Node must not authorize itself | Authorization comes from MCP via AG-LINK-000 |
| Node must not redefine capabilities | Capability identity/version resolved by MCP before reaching node |
| Node must not issue authority receipts | Authority receipts (qualification, seal, authorization) are Core-only |
| Node must not commit authoritative state | Governance state mutations are Core-only |
| Node must not bypass MCP dispatch | All capability invocations must pass through MCP for identity resolution |

## 5. Cross-Platform Invariant Tests

Every platform runtime must verify these invariants:

| Invariant | Verification |
|-----------|-------------|
| Same `ExecutionRequest` schema | Contract-compatible deserialization |
| Same receipt schema | Receipt validates against `execution-receipt.schema.json` |
| Same capability resolution rules | Tool name → handler mapping |
| Same AG-LINK authorization requirement | Missing/invalid auth → fail-closed |
| Different authority scopes enforced | Node rejects governance-only operations |

## 6. Relationship to Platform Adapters

```
Node Execution Runtime
         │
    ┌────┴────┐
    │         │
    ▼         ▼
Windows     Linux
Adapter     Adapter
(Rust)      (Rust — planned)

platform-specific execution only
no protocol authority
no governance authority
```

Platform adapters (Windows NSSM, Linux systemd, etc.) are **execution substrate only**.
They do not:
- Implement MCP
- Grant authorization
- Define capability meaning
- Issue governance receipts
